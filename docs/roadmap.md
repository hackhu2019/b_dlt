# Roadmap

本路线图的目标不是“多做功能”，而是避免项目边界失控。

当前优先级只围绕一个主线：

`Bilibili creator -> local files -> structured text -> searchable knowledge base`

## Current Scope

当前阶段只做五件事：

1. 拉取 UP 主视频清单
2. 下载音频或提取音频
3. 优先获取字幕，缺失时执行 ASR
4. 生成清洗文本、单视频总结、UP 主聚合总结
5. 建立本地 SQLite 全文检索索引

当前已经具备：

- `fetch_manifest.py`
- `download_audio.py`
- `export_bilibili_cookies.py`
- `transcribe.py`
- `summarize.py`
- `build_index.py`
- `run_creator_pipeline.py`

## Non-Goals

这些方向明确不在当前阶段：

- Web UI
- 向量数据库
- 生产部署
- 自动发布
- 数据库 schema 演进
- 多租户 / 账号系统
- 云端浏览器登录态托管
- 抓取“全站内容”而不是单个 UP 主

如果以后真的要做，必须先改文档，再改实现。

## Near-Term Priorities

### P0: 稳定现有链路

目标：

- 提升 `run_creator_pipeline` 在真实 B 站数据上的稳定性
- 减少鉴权、字幕、下载链路里的偶发失败
- 保证增量执行不会重复处理已完成产物

验收标准：

- 同一 UP 主重复运行时，产物不会无意义重算
- 常见错误能明确暴露在脚本输出里
- 文档和脚本参数保持一致

### P1: 提高可维护性

目标：

- 为关键编排路径补充更多测试
- 让错误输出更容易定位到具体阶段
- 保持脚本输入输出边界清晰

验收标准：

- 新增改动优先补单测而不是加临时日志
- 不引入与现有脚本并行重复的第二套实现

### P2: 改善知识库可用性

目标：

- 优化 Markdown 产物结构
- 优化 SQLite FTS 检索体验
- 明确导出到外部知识管理工具的最小格式

候选事项：

- 更稳定的 frontmatter 字段约定
- 更好的摘要结构模板
- `data/exports/` 的最小导出脚本

## Deferred Ideas

这些想法可以保留，但现在不做：

- Obsidian 插件或自动同步
- 简单本地 Web 浏览器
- 标签体系或主题聚类
- 向量搜索或 embedding 管道
- 多平台视频源扩展
- 云端批处理调度

它们不是“不允许”，只是当前阶段做了会分散注意力。

## Release Direction

短期版本方向：

- `0.1.x`
  以稳定工作流、修复真实数据问题、补文档为主

中期版本方向：

- `0.2.x`
  在不破坏本地优先原则的前提下，改善知识库导出和检索体验

在进入 `0.2.x` 之前，不引入新的基础设施依赖。

## Change Rules

如果一个新需求满足以下任意一条，先更新本路线图再动代码：

- 改变项目边界
- 新增核心依赖
- 引入新的顶级目录
- 让单脚本职责变成多职责
- 从“本地优先”转向“服务优先”

## Decision Filter

每次加功能前先问这三个问题：

1. 它是否直接提升 `manifest -> audio -> text -> index` 这条主链路？
2. 它是否能通过更少代码、更少依赖完成？
3. 它是否会让仓库更像产品平台，而不是本地工作流工具？

如果第 1 条答不上来，通常就不该现在做。
